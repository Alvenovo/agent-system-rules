# 交付门禁铁律（宣称完成前）

建了需求归档目录（`source/manifest.json` + 四件套）的正式测试交付，宣称完成前必须运行现有生成器的校验命令，完成条件是它输出以 `ok:` 开头且退出码为 0：

```
python "$HOME/.codex/测试规则/scripts/generate_test_package.py" --check "<需求归档目录>"
```

非 `ok` 时改 `source/manifest.json`、证据或缺失的输入材料，再由生成器重建四件套（产物不手改），然后重跑同一条命令直到 `ok`。未到 `ok` 只能报「未通过校验：原因」。没有归档目录的临时判定（一次性复现、单个缺陷现场）不走本门禁，按《测试执行精进规则.md》和 BUG 反馈规范留证据。校验范围见 `测试用例交付与归档.md` §二。

# 〇、写用例铁律（开写 JSON 前）

**材料先于用例。** 覆盖表和测试 manifest 之前，把本任务/需求给出的材料全部打开看完：需求文档（飞书/GitLab/本地 md）、前后端评审、流程图、Figma/UI、**禅道同需求下每个子任务的描述**（口径常写在开发任务里，需求正文没有）。有 Figma 链接或文件：先按系统级触发表登录，再对照每一页/每一帧。完成时已有材料核对表：每份材料标记已读，缺失项标记「受阻：原因」；每个成功标准都能追溯到材料位置。

**上游未完工先说，不硬测。** 开测前看禅道该需求的研发任务状态与需求阶段：Server / 前端任务未开始或未完成、阶段仍「研发中」，先把「本轮不具备完整测试条件、卡在哪条任务」告知用户；能测的照测，测不到的按受阻记，半成品页面的表现不当缺陷开单。

**判定深度先对一句。** 写用例前跟用户确认本轮判到哪一层：只判主流程能跑通（入口进得去、写请求真发出且返回成功、结果列表查得到；按钮错位、文案细节不判），还是含细项全量。任务名带「dev 环境配置」「环境验收」，或说明是短期快速实现、从 debug 环境继承来的，默认按冒烟口径并把这句口径说出口。口径写进归档的执行过程，复测沿用同一口径。

**归档先认产品。** 写用例前先按触发表读 `references\禅道访问.md`，再看禅道「所属产品」。路径 `D:\测试用例\{所属产品}\{YYYYMMDD}\{需求名-负责人}\`；根下没有该产品文件夹则新建。细则：`测试用例交付与归档.md`。

先完成覆盖表 A/B/C，再写测试 manifest。**A 列按需求「成功标准 / 不满足判定 / 本期验收」逐条落到稳定用例键或「受阻：原因」**；B 列沿用旧规则；C 列现网已有入口。完成时 A/B/C 每行均有稳定用例键或受阻原因。细则：`测试用例设计规范.md` §1.2。

**移动端 = iOS、Android、H5、小程序**，四端默认全测。跳过某端须需求原文点名。无包/无源码仍建条；执行走真机配合。细则：`测试用例设计规范.md`「端口成组」；执行：`真机配合.md`。

用户给出同事表或另一份用例表，要求对照覆盖、看区别、看要补充：先出覆盖对照 xlsx（桌面 + 归档日期目录，不进四件套），再按缺口补现行用例。细则：`覆盖对照表.md`。

**主流程先，用例人工可复验。** 每个需求先写、先判主流程那一条（入口 → 关键动作 → 用户侧最终看得见的结果），它不通则同需求细项停扩；步骤只写人在页面上做得出的动作，接口/数据库/日志核对收成 1 条专项。优先级按「这条不过主流程能不能走通」定，1 级只给会断主干的条。用例正文只写角色不写具体账号端口，换人能跑。细则：设计规范 §3、§5；执行精进 §二第 1 条。

**预期要能红。** 落笔前对每条预期问一句：实现真写出这个 bug，这条会变红吗？恒真（环境里没那东西却验「未出现」）与物理不可能（环境里出不了那东西却验「出现」）都是无效用例，比不写更糟。细则：设计规范 §4.12；自检第 ⑦ 项。

**执行与开缺陷。** 见 `测试执行精进规则.md`（含 `blocked_dependency`、开缺陷口径、**字面**判定）。

**字面。** 端点值、失败后再保存、保存后控件仍在。写步骤：设计规范 §4.11；判定：执行精进 §五第 12 条。
