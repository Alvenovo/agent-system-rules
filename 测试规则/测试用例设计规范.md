# 测试用例设计规范与方向（通用，系统级·完整版）

> 触发：编写 / 评审 / 修改 / 补充测试用例、生成用例 CSV/XLSX 前，**必须先完整读取本文件**再执行。
> 适用于所有项目；各项目可在项目级 AGENTS.md 中修改、补充本规范，**项目级规则优先于系统级**。

## 1. 写前材料（未看完禁止开写）

用户给出的需求文档、前后端评审纪要、Figma/UI、流程图（文本、链接或附件）都必须打开对照，**看完再写覆盖表和用例**。飞书按系统级方法处理；有 Figma 先按触发表 `%USERPROFILE%\.codex\references\Figma访问.md` 登录，再打开每一页/每一帧；禅道按同目录 `测试规则.md`。不要因为「可能冲突」就跳过链接。

- **成功标准**：从「目标与成功标准 / Goals & Success Criteria / 不满足判定 / 验收标准」逐条抽出，写成可执行步骤（操作 + 可判定预期）。章节标题不当用例名。覆盖表 A 先落这些行；齐了再写筛选和文案条。
- 流程图和评审纪要补关键业务路径；「测试重点」用来核对 A 是否缺条，不替代成功标准。
- Figma 每一帧/每一张图的标题当作对应场景，对照需求写用例。
- 多语言、主题色、布局适配：不强制单开专项，以免撑条数。
  - **多语言**：材料里出现语言切换入口，或同一界面有中英两套文案，才写语言用例；收成 1 条、2–4 步（切换后文案刷新 + 混排/缓存旧文案），不要拆成 5 条。商品名里的英文专有名词（如 ROG、SKU）不算多语言。
  - **主题色 / 布局**：Figma 或需求里写了具体值（主题色、位置、展示形态），写进对应步骤的预期即可，不另开「主题适配」「布局兼容」专项。

### 1.2 覆盖表（硬门禁；表未齐禁止写 JSON）

写用例不是「把本期飞书新增点写成约 10 条」。先填覆盖表，再写用例、再收条数。

完成标准：下表 **A/B/C 每一行**都有「对应用例编号」或「受阻：原因」。成功标准 / 不满足判定 / 本期验收有一条空白 = 未完成。

| 列 | 从哪抽 | 抽什么 |
| --- | --- | --- |
| A 当期 | 「目标与成功标准」「不满足判定」「验收标准」；本迭代新交互；同文档「测试重点」里属于本期的条目 | 成功标准每一条的可判定步骤；新字段、新文案、新跳转、新端口 |
| B 回归 | 正文「沿用 / 同之前 / 逻辑不变」；目录里更早的迭代章节 | 旧公式、生效条件、状态机、权限隔离、活动互斥 |
| C 现网 | **打开**该功能列表/编辑页（只读），记下会被本次改动碰到的已有入口 | 操作列（复制/上架/下架/删除）、导入/导出、筛选、批量、空值、重复添加 |

抽 A 列时：有成功标准 / 不满足判定 / 验收标准就按条目打勾，每条写成可执行步骤。写进本期成功标准的 C 端可见性归 A。测试重点用来核对 A 是否缺条，不拿功能说明或筛选章节代替成功标准。
抽 B 列时：历史章节和「沿用旧逻辑」往下翻完；预期抄旧规则可判定原文。
抽 C 列时：页面上看见的按钮/列都进表，含复制等现有操作，不要求需求正文再写一遍。触及移动端时覆盖表必须有 iOS、Android、H5、小程序四行（文档点名某端不测则该行写「不做：原文」）；触及 PC 再加 PC 行（§3.4）。

材料写「沿用旧逻辑 / 与之前一致」时，预期里抄旧规则的可判定原文（字段名、公式、文案、URL）。只写「与原来一致」不算覆盖。

环境不具备（缺第二店铺、缺活动商品、无小程序源码）：覆盖表仍建行，用例仍建条，执行状态标受阻。不因缺数据把该行从覆盖表删掉。

## 2. 覆盖方向（维度）

按需求实际情况选择维度。安全/性能/多浏览器不强制单开专项。§1.2 覆盖表 A/B/C 三列、以及触及用户端时的端口成组（§3.4）强制覆盖，不在「可不选」之列。核心业务至少包含：功能、接口、数据库、权限（权限/隔离环境不具备则建条标受阻）。

- 功能：正常流程；异常流程（参数缺失/格式错误/超限/类型错误/非法值/重复提交/状态不满足）；边界（最小/最大/临界/空值/特殊字符/超长）；状态流转（创建/编辑/删除/审核/发布/下架/恢复等）。
- 接口：请求（Method/URL/Header/鉴权/参数/Content-Type）；响应（状态码、code/message/data、字段完整性与类型、数据准确性）；业务链路（登录→Token→创建→查询→修改→删除）。
- 数据库：一致性（接口返回与库一致、增删改正确入库）；完整性（主键/非空/默认值/外键）；异常（重复/脏数据/越权/删除恢复）。
- 权限：未登录/Token 失效/过期；角色权限；水平/垂直越权。
- 安全：SQL 注入、XSS、特殊字符过滤、Token 泄露、参数篡改、重放。
- 性能：压力/并发、TPS/QPS、响应时间、错误率、CPU/内存、稳定性；无明确指标时以“不卡死、不超时”为兜底标准。
- 兼容：浏览器（Chrome/Edge/Firefox）、系统、多端（PC + 移动端 iOS/Android/H5/小程序）、不同分辨率/机型。
- 日志与异常：异常是否产生正确日志、日志含关键参数、错误信息明确、异常被正确捕获。

## 3. 用例整合与精简（编写方式）

只出一套用例（工作区 `cases_*.json` → 归档四件套），按这一套执行，不另做执行套/交付套。

**条数（软约束，非硬性上下限）**：覆盖表齐了之后再收条数。默认 **8–20 条**，能合并到约 10 条最好。特别简单可低于 8；特别难/多端/覆盖表行多可超过 20。覆盖表未齐时不准停写。

**每条步骤**：默认 **2–4 步**，一条只覆盖一组可一起复测的场景。不要把整条需求塞进 5 步以上的长流程（中间一步没过就要整条重测）；也不要按每个检查点拆成十几条重复用例。

遵循“最少用例覆盖最多场景”，能合并的一律合并，禁止冗余拆条：

1. 同一个功能的正向/反向、边界、状态流转等关联场景，尽量合并进同一条用例的多个步骤（仍受上面 2–4 步约束；超出就拆成相邻几条，不拆成重复用例）。
2. 优先设计“一条连续操作流程串完多个场景”的用例，但单条不要超过 4 步。测试数据仍“一次构造、多场景复用”。
3. 测试数据“一次构造、多场景复用”，通过连续操作自然覆盖多个场景，不为每个场景单独准备数据。
4. **端口成组（硬门禁）**：**移动端 = iOS、Android、H5、小程序**，四端默认全测、所属模块分开。触及用户端展示/跳转/下单时这四端都要有用例。只有需求/飞书/评审/同事表**原文点名**某一端「不测 / 不做 / 本期不改」才跳过该端：覆盖表该行写「不做：原文」，不按功能条展开；原文是「本期不改 / 无入口」时可留 1 条反向确认。材料只写「移动端」、入口清单只有 H5、本机无 App 包/无小程序源码，都不是跳过理由——无包仍建条；执行 Android/iOS 走真机配合（用户手机无法测该端才标受阻）。触及 PC 则 PC 另组成条；材料写明不测 PC 则 PC 行写「不做：原文」。后台-only 不拆 C 端。装修后台若有 Android / iOS / WAP / 小程序 平台切换，每个平台都要有对应用例。同一端的同类反向场景可收成 1 条，不必每端都拆成 4 条。专项维度（§3.6）不按端口重复。
5. 需求中的示例场景必须命中，但测试数据可等价调整，不必逐字复刻需求描述。
6. 专项维度（接口过滤、数据库一致性、兼容性、性能、异常兜底等）每个维度合并为一条，不按平台重复。
7. 生成后自检顺序：① 成功标准、不满足判定、本期验收每条都有用例编号或受阻；② 覆盖表 A/B/C 其余行都有编号或受阻；③ 触及移动端时 iOS / Android / H5 / 小程序 四行都有编号或「不做：原文」（原文须点名该端）；④ 每条 2–4 步、条数再往 8–20 收。只过 ④ 不过 ①②③ 不算完成。
8. 可以不单开的：性能压测、多浏览器兼容。覆盖表 B/C 里的导入、隔离、同页已有入口、测试重点条目：建条；环境不具备标受阻。
9. **已被覆盖的场景不重复建用例**：某步骤已在其他用例中测过，就不为它单独开一条；相同步骤不允许跨用例重复测。例如每个活动模块的用例已含模糊搜索正向/反向步骤时，不再另建“模糊搜索专项”。
10. **多模块同一需求**：模块用例保留（便于逐模块执行、不漏），但步骤模板化精简到每条 2~4 步；通用异常/边界场景合并成少量专项用例（通常 3~6 条），不按模块重复展开。总条数仍按本节软约束控制。
11. 生成后自检“有无重复步骤、可被覆盖的用例、低收益用例”，有就删/合并后再交付；删之前先确认该场景仍能在覆盖表某行的步骤里测到。

## 4. 高频易忽略点（评审沉淀，生成后必须对照）

1. 页面展示的业务字段，步骤与预期必须同步核对数据库对应字段；同一批同类用例全部补，不能只补第一条。
2. 需求新增筛选/搜索字段时，单独建用例检查字段展示、位置与可搜索性；每种输入（错误/空格/表情/特殊符号/不存在值）单独成步骤、预期一一对应，不能合并成一步。成功标准行齐了再写筛选专项。
3. 同时有列表和【查看详情】时，字段校验必须双范围覆盖。
4. 状态流转后检查“另一侧”列表（如在售列表不应出现下架操作人字段）；再次操作后信息必须为最新。
5. 批量操作必须覆盖全部对象 + 字段顺序/配套展示。
6. 日志/记录类和经营口径都要反向断言：不应产生的记录不存在；新对象按规定不计入库存/销量/发布数量/搜索/同步时，步骤里核对「未增加 / 未同步」。先与开发确认查看位置，以及失败操作是否记录。
7. 产品/开发未确认的业务逻辑：场景重要则仍建条，预期和备注写「待确认 / 需与产品/开发确认后再执行」，禁止填猜测的具体值。需求没写但 Figma 上能看见的文案/URL/布局，按 Figma 写，这不算猜。所有材料都没有的，不按「更贴近用户场景」补预期。
8. 写权限、数据隔离、越权用例前，先确认账号与店铺/角色等数据模型关系；设计上没有该隔离则不写。设计上有、只是本机缺账号：仍建条，标受阻。
9. 搜索/筛选先确认匹配规则与字段语义（精确/模糊、SPU/SKU、账号名/手机号等），不混用标识。
10. 同模块迭代（加渠道、加字段、改文案）：B 列旧规则和 C 列现网入口必须进覆盖表，不能只测新增点。
11. 同一流程存在弱校验（保存/草稿）和强校验（提交/发布）时拆开测：弱校验允许的缺项和重复值，提交时按正式规则拦截；首次保存失败不落库，与已有记录提交失败仍保留，分步写预期。独立业务规则（如数量上限与有效期）拆成相邻条，不塞进一条。

## 5. 格式硬性要求

- 步骤/预期编号：`数字 + 英文句点 + 空格`（如 `1. `），严禁 `1、`；步骤与预期条数一一对应。
- **预期禁止泛化**：禁止只写「内容与需求一致」「展示正确」「文案正确」「URL 一致」「与原来一致」「沿用旧逻辑」。材料里已有的标题、按钮/提示文案、跳转 URL、接口、配置值、列表项、可见布局/状态、旧规则公式/生效条件，必须写进对应步骤的预期。没有明确值的仍按第 4 节第 7 条标注待确认，不编造。
  - 不要写：卡片主标题存在，内容与需求一致。应该写：主标题为「……」（需求/Figma 原文）。
  - 不要写：跳转 URL 正确。应该写：跳转到 `https://…`（材料原文）。
- **所属模块**：从需求场景提炼叶子名，不带斜杠层级；需要二级时用下划线，如 `登录_PC端`、`营销_限时抢购`。
- **关键词**：`{所属模块}_{本条关键词}`，如 `入口展示_主板型号准入`。
- 优先级：数字 1/2/3/4（1 最高），不用 ①。分配：1 核心业务/关键路径/阻断；2 次要功能、常见异常；3 UI 细节、提示文案、极低频；4 兼容或环境受阻（覆盖表 B/C 的受阻条用 4，仍建条，不删）。
- 用例编号：`TC_模块_001`，同模块连续编号；测试结果、用例备注列导入时留空。
- 禅道导入 CSV：12 列固定（所属模块、用例编号、关键词、优先级、用例名称、前置条件、步骤、预期、测试结果（留空）、用例备注、用例类型、适用阶段）。
- **CSV 必须走 skill `禅道用例CSV`**：以源数据 JSON 为输入，运行 `%USERPROFILE%\.codex\skills\禅道用例CSV\scripts\generate_zentao_csv.mjs` 生成；**禁止手写 CSV**。系统级 12 列红线已覆盖时，不必重复读 skill 的 `format.md`。
- xlsx：从同一份源数据 JSON 生成；数据单元格自动换行、数据行不设固定行高，保证长文本打开完整显示。

## 7. 新项目测试用例编写流程

1. 先向用户展示本文件全部要点。
2. 询问用户：针对当前项目，用例编写规范与方向需要更改或补充什么。
3. 将用户确认的内容写入**项目级** `AGENTS.md` 或 `.cursor/rules/`，作为该项目用例规范，项目级优先。
4. 确认后再开始编写；同一项目后续直接按项目级规则执行，无需重复展示。
