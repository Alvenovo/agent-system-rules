# 测试用例设计规范与方向（通用，系统级·完整版）

> 触发：编写 / 评审 / 修改 / 补充测试用例、生成用例 CSV/XLSX 前，**必须先完整读取本文件**再执行。
> 适用于所有项目；各项目可在项目级 AGENTS.md 中修改、补充本规范，**项目级规则优先于系统级**。

## 1. 写前材料

用户给出的需求文档、前后端评审纪要、Figma/UI、流程图（文本、链接或附件）都要打开对照。飞书按系统级方法处理；有 Figma 先按触发表 `%USERPROFILE%\.codex\references\Figma访问.md` 登录，再打开每一页/每一帧；禅道按 `%USERPROFILE%\.codex\references\禅道访问.md`。完成时 manifest 的 `materials` 已列出每份材料及其状态；已取得的材料标记 `read`，缺失项标记 `blocked` 并写明原因。

- **成功标准**：从「目标与成功标准 / Goals & Success Criteria / 不满足判定 / 验收标准」逐条抽出，写成可执行步骤（操作 + 可判定预期）。章节标题不当用例名。覆盖表 A 先落这些行；齐了再写筛选和文案条。
- 流程图和评审纪要补关键业务路径；「测试重点」用来核对 A 是否缺条，不替代成功标准。
- Figma 每一帧/每一张图的标题当作对应场景，对照需求写用例。
- 多语言、主题色、布局适配：不强制单开专项，以免撑条数。
  - **多语言**：材料里出现语言切换入口，或同一界面有中英两套文案，才写语言用例；收成 1 条、2–4 步（切换后文案刷新 + 混排/缓存旧文案），不要拆成 5 条。商品名里的英文专有名词（如 ROG、SKU）不算多语言。
  - **主题色 / 布局**：Figma 或需求里写了具体值（主题色、位置、展示形态），写进对应步骤的预期即可，不另开「主题适配」「布局兼容」专项。

### 1.2 覆盖表（硬门禁）

写用例不是「把本期飞书新增点写成约 10 条」。先填覆盖表，再写用例、再收条数。

覆盖表写入 manifest 的 `coverage`，与用例一起永久归档。完成标准：下表 **A/B/C 每一行**都有稳定 `case_key`，或状态为 `blocked` / `not_applicable` 并写明原因。成功标准、不满足判定、本期验收没有未解释空行。

| 列 | 从哪抽 | 抽什么 |
| --- | --- | --- |
| A 当期 | 「目标与成功标准」「不满足判定」「验收标准」；本迭代新交互；同文档「测试重点」里属于本期的条目 | 成功标准每一条的可判定步骤；新字段、新文案、新跳转、新端口 |
| B 回归 | 正文「沿用 / 同之前 / 逻辑不变」；目录里更早的迭代章节 | 旧公式、生效条件、状态机、权限隔离、活动互斥 |
| C 现网 | **打开**该功能列表/编辑页（只读），记下会被本次改动碰到的已有入口 | 操作列（复制/上架/下架/删除）、导入/导出、筛选、批量、空值、重复添加 |

抽 A 列时：有成功标准 / 不满足判定 / 验收标准就按条目打勾，每条写成可执行步骤。写进本期成功标准的 C 端可见性归 A。测试重点用来核对 A 是否缺条，不拿功能说明或筛选章节代替成功标准。
抽 B 列时：历史章节和「沿用旧逻辑」往下翻完；预期抄旧规则可判定原文。
抽 C 列时：页面上看见的按钮/列都进表，含复制等现有操作，不要求需求正文再写一遍。触及移动端时覆盖表必须有 iOS、Android、H5、小程序四行（文档点名某端不测则该行写「不做：原文」）；触及 PC 再加 PC 行（见「端口成组」）。

材料写「沿用旧逻辑 / 与之前一致」时，预期里抄旧规则的可判定原文（字段名、公式、文案、URL）。只写「与原来一致」不算覆盖。

环境不具备（缺第二店铺、缺活动商品、用户无法在手机上测试该端）：覆盖表仍建行，用例仍建条，执行状态使用 `blocked_environment`。无小程序源码时仍走真机配合，不标受阻。

## 2. 覆盖方向（维度）

按需求实际情况选择维度。安全/性能/多浏览器不强制单开专项。§1.2 覆盖表 A/B/C 三列、以及触及用户端时的端口成组强制覆盖，不在「可不选」之列。核心业务至少包含：功能、接口、数据库、权限（权限/隔离环境不具备则建条标受阻）。接口、数据库、日志三项各收成 1 条专项用例（§3「人工可复验」），不摊进每条功能用例。

- 功能：正常流程；异常流程（参数缺失/格式错误/超限/类型错误/非法值/重复提交/状态不满足）；边界（最小/最大/临界/空值/特殊字符/超长）；状态流转（创建/编辑/删除/审核/发布/下架/恢复等）。
- 接口：请求（Method/URL/Header/鉴权/参数/Content-Type）；响应（状态码、code/message/data、字段完整性与类型、数据准确性）；业务链路（登录→Token→创建→查询→修改→删除）。
- 数据库：一致性（接口返回与库一致、增删改正确入库）；完整性（主键/非空/默认值/外键）；异常（重复/脏数据/越权/删除恢复）。
- 权限：未登录/Token 失效/过期；角色权限；水平/垂直越权。
- 安全：SQL 注入、XSS、特殊字符过滤、Token 泄露、参数篡改、重放。
- 性能：压力/并发、TPS/QPS、响应时间、错误率、CPU/内存、稳定性；无明确指标时以“不卡死、不超时”为兜底标准。
- 兼容：浏览器（Chrome/Edge/Firefox）、系统、多端（PC + 移动端 iOS/Android/H5/小程序）、不同分辨率/机型。
- 日志与异常：异常是否产生正确日志、日志含关键参数、错误信息明确、异常被正确捕获。

## 3. 用例整合与精简（编写方式）

只维护一份测试 manifest，由它生成归档四件套；用例、覆盖表、执行状态和证据映射都回写该 manifest。

**先写主流程条。** 每个需求/模块先写那条端到端主流程并排在最前：从入口（登录/进线）起步 → 完成本需求的关键动作 → 落到用户最终看得见的结果。主流程条写出来之前不铺细项；主流程条在执行中判不过，同需求的细项停止扩写。

**人工可复验。** 每一步是人在页面上做得出的一个动作，每条预期是人眼当场判得的一句话（文案原文、数值、状态、跳转、有没有）。需要 F12、SQL、日志才能判的核对，收进那 1 条专项用例并写明看哪个请求/哪个字段，不散嵌在流程条里。非界面观测（进程、设备占用、日志、接口字段、库表）同理：把判别特征写进前置——看哪个进程、哪条曲线、哪个字段，什么命名或量级算哪一类，并写明哪个信号不作证据；「看一下系统 / 看一下后台」不是预期。自检：把某一步交给同事，他不问开发就能做下去并答出「对 / 不对」，这一步才算写成了。

**条数（软约束，非硬性上下限）**：覆盖表齐了之后再收条数。默认 **8–20 条**。特别简单可低于 8；特别难、多端或覆盖表行多可超过 20。条数调整不能留下未映射的覆盖项。

**每条步骤**：默认 **2–4 步**，一条只覆盖一组可一起复测的场景。不要把整条需求塞进 5 步以上的长流程（中间一步没过就要整条重测）；也不要按每个检查点拆成十几条重复用例。

遵循“最少用例覆盖最多场景”，能合并的一律合并，禁止冗余拆条：

1. 同一个功能的正向/反向、边界、状态流转等关联场景，尽量合并进同一条用例的多个步骤（仍受上面 2–4 步约束；超出就拆成相邻几条，不拆成重复用例）。
2. 优先设计“一条连续操作流程串完多个场景”的用例，但单条不要超过 4 步。测试数据仍“一次构造、多场景复用”。
3. 测试数据“一次构造、多场景复用”，通过连续操作自然覆盖多个场景，不为每个场景单独准备数据。
4. **端口成组（硬门禁）**：**移动端 = iOS、Android、H5、小程序**，WAP 是 H5 的别名，不另算一端。四端默认全测、所属模块分开。触及用户端展示/跳转/下单时这四端都要有用例。只有需求/飞书/评审/同事表**原文点名**某一端「不测 / 不做 / 本期不改」才跳过该端：覆盖表该行写原文并标记 `not_applicable`，不按功能条展开；原文是「本期不改 / 无入口」时可留 1 条反向确认。材料只写「移动端」、入口清单只有 H5、本机无 App 包/无小程序源码，都不是跳过理由——无包或无源码仍建条；四端执行都走真机配合（用户手机无法测该端才标 `blocked_environment`）。触及 PC 则 PC 另组成条；材料写明不测 PC 时标记 `not_applicable`。后台-only 不拆 C 端。装修后台若有 Android / iOS / WAP / 小程序平台切换，每个平台都要有对应用例，其中 WAP 归入 H5 组。同一端的同类反向场景可收成 1 条，不必每端都拆成 4 条。专项维度（本节第 6 项）不按端口重复。
5. 需求中的示例场景必须命中，但测试数据可等价调整，不必逐字复刻需求描述。
6. 专项维度（接口过滤、数据库一致性、兼容性、性能、异常兜底等）每个维度合并为一条，不按平台重复。
7. 生成后自检顺序：① 每个需求/模块都有 1 条主流程条且排在最前；② 成功标准、不满足判定、本期验收每条都有 `case_key` 或带原因的阻塞状态；③ 覆盖表 A/B/C 其余行都有 `case_key` 或带原因的阻塞状态；④ 触及移动端时 iOS / Android / H5 / 小程序四行都有 `case_key` 或材料原文支持的 `not_applicable`；⑤ 每条默认 2–4 步，逐步都能人工复验（§3「人工可复验」），再按覆盖复杂度调整条数；⑥ 前置条件、步骤、预期里只有角色和入口，换个人拿到这份用例也能照跑（§5「可移植」）；⑦ 每条预期都能红，没有恒真与物理不可能（§4.12）。完成时七项全部通过。
8. 可以不单开的：性能压测、多浏览器兼容。覆盖表 B/C 里的导入、隔离、同页已有入口、测试重点条目：建条；环境不具备标受阻。
9. **已被覆盖的场景不重复建用例**：某步骤已在其他用例中测过，就不为它单独开一条；相同步骤不允许跨用例重复测。例如每个活动模块的用例已含模糊搜索正向/反向步骤时，不再另建“模糊搜索专项”。
10. **多模块同一需求**：模块用例保留（便于逐模块执行、不漏），但步骤模板化精简到每条 2~4 步；通用异常/边界场景合并成少量专项用例（通常 3~6 条），不按模块重复展开。总条数仍按本节软约束控制。
11. 生成后自检“有无重复步骤、可被覆盖的用例、低收益用例”，有就删/合并后再交付；删之前先确认该场景仍能在覆盖表某行的步骤里测到。

## 4. 高频易忽略点（评审沉淀，生成后必须对照）

1. 页面展示的业务字段，在接口/数据库专项那 1 条里核对数据库对应字段；同一批同类字段全部进这条，不能只核对第一个。功能条的步骤保持人工可复验（§3「人工可复验」）。
2. 需求新增筛选/搜索字段时，单独建用例检查字段展示、位置与可搜索性；每种输入（错误/空格/表情/特殊符号/不存在值）单独成步骤、预期一一对应，不能合并成一步。成功标准行齐了再写筛选专项。
3. 同时有列表和【查看详情】时，字段校验必须双范围覆盖。
4. 状态流转后检查“另一侧”列表（如在售列表不应出现下架操作人字段）；再次操作后信息必须为最新。
5. 批量操作必须覆盖全部对象 + 字段顺序/配套展示。
6. 日志/记录类和经营口径都要反向断言：不应产生的记录不存在；新对象按规定不计入库存/销量/发布数量/搜索/同步时，步骤里核对「未增加 / 未同步」。先与开发确认查看位置，以及失败操作是否记录。
7. 产品/开发未确认的业务逻辑：场景重要则仍建条，预期和备注写「待确认 / 需与产品/开发确认后再执行」，禁止填猜测的具体值。需求没写但 Figma 上能看见的文案/URL/布局，按 Figma 写，这不算猜。所有材料都没有的，不按「更贴近用户场景」补预期。
8. 写权限、数据隔离、越权用例前，先确认账号与店铺/角色等数据模型关系；设计上没有该隔离则不写。设计上有、只是本机缺账号：仍建条，标受阻。
9. 搜索/筛选先确认匹配规则与字段语义（精确/模糊、SPU/SKU、账号名/手机号等），不混用标识。
10. 同模块迭代（加渠道、加字段、改文案）：B 列旧规则和 C 列现网入口必须进覆盖表，不能只测新增点。
11. 同一流程存在弱校验（保存/草稿）和强校验（提交/发布）时拆开测：弱校验允许的缺项和重复值，提交时按正式规则拦截；首次保存失败不落库，与已有记录提交失败仍保留，分步写预期。**字面**三点各成步骤：合法区间用端点值（非负写 0，不超过 N 写 N），非法侧另步；强校验失败后立刻再点弱保存，预期仍走弱规则；保存后发布还依赖的选项（发布状态等）核对该步仍展示且可改，发布去向另步。独立业务规则（如数量上限与有效期）拆成相邻条。完成：三点都有步骤，或需求原文没有对应句。
12. **预期要能红。** 落笔前对每条预期问一句：实现真写出这个 bug，这条会变红吗？两种不变红都是无效用例，比不写更糟（占条数、花执行时间、让「已覆盖」变成谎话）：被测对象在环境里不存在（环境里没有该硬件 / 该角色 / 该数据，却验「未出现 X」，恒真）；结果被环境锁死（环境里不可能产生 X，却验「出现 X」，不可能）。不变红就换环境、换前置或删条；预期由多个独立条件决定时，换前置的同时在前置写全组合表（每行一个组合、对应预期、对应用例编号）——单个条件不是充分条件，不写全组合读者会拿一个条件推预期，把对的预期当写错。负向预期（未启用 / 不报错 / 回落 / 不影响）先查：它成立是因为逻辑对，还是因为环境里那个东西根本不存在。
13. **多环境写分配与顺序。** 多台机器或多个环境执行时，前置写清：哪个环境跑哪几条、顺序约束（先跑改动前的状态，再切到改动后的状态跑其余条）、某个环境**不验**什么及原因。顺序不写，前后用例互相污染前置。
14. **反直觉预期挂材料出处。** 预期与直觉相反时，在预期里引材料条款号加原文短语。不挂出处，执行者与评审会把它当笔误「改正」掉。实现真与材料冲突时，那是缺陷线索，不是改用例的理由——拿到开发 / 产品原话再改，并标注新口径出处。

## 5. 格式硬性要求

- 步骤/预期编号：`数字 + 英文句点 + 空格`（如 `1. `），严禁 `1、`；步骤与预期条数一一对应。
- **预期禁止泛化**：禁止只写「内容与需求一致」「展示正确」「文案正确」「URL 一致」「与原来一致」「沿用旧逻辑」。材料里已有的标题、按钮/提示文案、跳转 URL、接口、配置值、列表项、可见布局/状态、旧规则公式/生效条件，必须写进对应步骤的预期。没有明确值的仍按第 4 节第 7 条标注待确认，不编造。
  - 不要写：卡片主标题存在，内容与需求一致。应该写：主标题为「……」（需求/Figma 原文）。
  - 不要写：跳转 URL 正确。应该写：跳转到 `https://…`（材料原文）。
- **所属模块**：从需求场景提炼叶子名，不带斜杠层级；需要二级时用下划线，如 `登录_PC端`、`营销_限时抢购`。
- **关键词**：`{所属模块}_{本条关键词}`，如 `入口展示_主板型号准入`。
- **可移植**：前置条件、步骤、预期只写角色和入口（管理员账号 / 平台客服账号 / 店铺客服账号 / 测试会员 A / 客服后台登录入口），换个人拿到这份用例也能照跑。具体账号口令、本机端口与 profile、执行人姓名、截图水印名留在项目 `AGENTS.md`、《环境手册》和账号名册里，不进用例正文；`execution.note` 是内部执行记录，可以写实。
- 优先级：数字 1/2/3/4（1 最高），不用 ①。**按「这条不过，主流程还能不能走通」定级**，逐条判，不整批给 1：
  - **1**：这条不过主流程就走不通或结果错——主流程条本身、它必经的前置能力、它依赖的数据与下发。
  - **2**：主流程能走通，但本期新增或变更的某项功能不对（次要功能、常见异常、回归项、配置与筛选）。
  - **3**：只影响文案、提示语、UI 细节、极低频路径。
  - **4**：本期不测或测不了的条（兼容、覆盖表 B/C 的受阻条，仍建条不删）；以及接口/字段专项条——它守的东西已在 1～3 的条里判过，只为归口机器核对而存在。
  - 交付前自检：每条 1 级都要能说出「它断了主流程哪一步走不下去」；说不出就降到 2。
  - **校准先验**：一个需求的 1 级通常只有 1–3 条（主流程条 + 它必经的前置能力）。超过 3 条先怀疑自己把「这条很重要」当成了「这条断主干」——配置校验、文案、权限矩阵、回归项再重要也是 2。
- `case_key`：创建后保持不变，用于关联覆盖项、状态和证据；展示编号 `TC_模块_001` 可由生成器随排序重建。
- 禅道导入 CSV：12 列固定（所属模块、用例编号、关键词、优先级、用例名称、前置条件、步骤、预期、测试结果（留空）、用例备注、用例类型、适用阶段）。
- 四件套运行 `python "$HOME/.codex/测试规则/scripts/generate_test_package.py" "<manifest.json>" "<归档目录>"` 统一生成；校验按《测试规则.md》交付门禁。独立 CSV 转换才使用 skill `禅道用例CSV`。
- xlsx 数据单元格自动换行、数据行不设固定行高，保证长文本打开完整显示。

## 7. 新项目测试用例编写流程

首次只向用户确认会改变执行边界的默认值：四端覆盖、覆盖表门禁、归档产品与路径、测试环境写入授权，以及项目相对系统规则的差异。把用户确认的差异写入项目级 `AGENTS.md` 或 `.cursor/rules/`；没有差异则不复制系统规则。完成时项目差异已记录，或用户明确采用系统默认。
