# 覆盖对照表（对照同事表 / 另一份用例表）

> 触发：用户给出同事或他人的用例表（xlsx / csv / 飞书），要求对照覆盖率、看区别、看要补充什么。未命中不要读本文件。

对照完成后，**主动写出 xlsx**，不要等用户再说「发我一份」。

## 1. 怎么对

1. 抽出对方表每一行作为一个检查点（编号、标题、步骤、预期都看；第二步预期为空的仍算一个点）。
2. 映射到现行 `source/manifest.json` 的稳定 `case_key`：已覆盖 / 已覆盖（合并）/ 漏 / 偏弱。
3. 列出我方有、对方没有的点（入库字段、现网入口、待确认项），不要删。
4. 对方「与原来一致 / 沿用旧逻辑」不算覆盖；对方 1 步拆条不要搬回现行用例。
5. 漏和偏弱：能合并进现有 2–4 步的就合并，不能合并再加相邻条。补完后更新 manifest 并统一生成四件套。

完成标准：每个对方检查点都有「现行用例编号」或「不补：原因」；xlsx 已写出。

## 2. 对照 xlsx

固定四个工作表：

| 表 | 内容 |
| --- | --- |
| 概要 | 对照日期、对方表来源与条数、现行条数、条数差怎么读、对照结论、归档路径 |
| 对方检查点对照 | 对方编号、模块、场景、对照结果、现行用例 |
| 该补的点 | 优先级、对方编号、场景、对照时现状、补进现行（或「不补：原因」） |
| 我方多出来的 | 现行用例、对方没有的点 |

数据单元格自动换行，数据行不设固定行高。对照结果用字面量：已覆盖、已覆盖（合并）、漏、偏弱、对照后已补、不补。

文件名：`{项目名}-{需求简称}-覆盖对照.xlsx`。需求编号写成 `字母_数字`。

## 3. 放哪里

写两份，路径告诉用户（桌面这份便于转发）：

1. 桌面：`%USERPROFILE%\Desktop\{文件名}`
2. 归档日期目录（与需求文件夹**同级**）：`D:\测试用例\{禅道所属产品}\{YYYYMMDD}\{文件名}`

不放进 `{需求名-负责人}` 四件套文件夹，不参与四件套条数校验。
