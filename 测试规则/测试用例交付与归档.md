# 测试用例交付、同步、归档与 BUG 反馈规范（通用，系统级·完整版）

> 触发：生成或同步用例四件套、处理组长评审表（文件名含 `reviewed by`）、收集/归档执行证据、写 BUG 反馈、归档用例文件前，**必须先完整读取本文件**再执行。

## 一、交付与同步

- 产出物：用例 xlsx、禅道导入 CSV、执行状态清单、执行过程手册、源数据 JSON；改动其中任何一个，其余必须同步。查看版 xlsx 始终是现行版本。
- 执行状态如实标注：已实测通过 / 部分验证 / 当前环境受阻 / 疑似缺陷 / 未执行，并附实测说明；禁止把未验证的写成已验证。因前置主功能失败而未跑的条标「当前环境受阻」（写明前置编号），不标「疑似缺陷」、不按跳过条拆 BUG。
- 必须配套《执行过程.md》：环境、账号、页面路径、数据准备、覆盖表 A/B/C（每行对应用例编号或受阻原因）、逐条步骤与预期，保证新人可复现。
- 对照同事表或另一份用例表时另出覆盖对照 xlsx，放桌面和归档日期目录，不进需求四件套文件夹。细则：`覆盖对照表.md`。

## 二、测试用例文件同步规则（全局适用）

无论用户要求改动其中哪一个（改用例、加用例、删用例、重编号、调顺序、改预期等），都必须在同一次操作中把该需求/模块的其余产出文件全部同步，保持编号、内容、条数完全一致；禁止只改其中一份就交付。

1. 以源数据 JSON（如 `cases_funXXXX_corrected.json`）为唯一数据源，重新生成 xlsx、CSV、执行状态清单、执行过程手册，避免手工逐个修改。其中禅道导入 CSV **必须**走 `skills\禅道用例CSV\scripts\generate_zentao_csv.mjs`，禁止手写或从 xlsx 另存为 CSV。
2. 执行状态清单同步时保留已有的执行状态（已实测通过 / 部分验证 / 当前环境受阻 / 疑似缺陷 / 未执行）及实测说明；新增用例标“未执行”，删除用例移除对应行，重编号后状态跟随用例内容走。
3. 同步完成后校验：CSV 为 12 列且条数与 xlsx 一致；执行过程手册用例标题数与条数一致；状态清单行数与条数一致；步骤与预期一一对应。
4. 文件归档按《测试用例文件归档规则》执行。项目级 `AGENTS.md` 只写本产品名；路径结构以本文件为准。

## 三、测试用例文件归档规则（通用，系统级）

1. 每次生成测试用例文件（CSV、XLSX、执行过程 MD 等）后，必须归档到独立文件夹：
   - 默认根目录 `D:\测试用例`
   - 路径：`D:\测试用例\{禅道所属产品}\{YYYYMMDD}\{需求名-负责人}\`
   - `{禅道所属产品}` 与禅道该任务/需求的「所属产品」一致（如 `华硕新商城`、`华硕客服`、`华硕会员商城`、`华硕小二`）。写用例前先读这一格；根下没有同名文件夹则新建。不按禅道执行名再套一层。
   - Cursor 工作区（桌面对话文件夹）不随新产品自动创建；桌面已有该产品目录则在其中操作。
2. 日期子文件夹已存在则直接复用，不重复创建；每个产品下每个日期只保留一个子文件夹。
3. 文件命名约定（`{项目名}` 即禅道所属产品名；`{需求编号}` `{需求名}` 取自归档文件夹，如 `fun_0377-商品发布支持草稿箱功能-王文东` → 编号 `fun_0377`、需求名 `商品发布支持草稿箱功能`，不含负责人）：
   - `{项目名}-功能测试用例-byAI.csv`（禅道导入用）
   - `{项目名}-_{需求编号}_{需求名}.xlsx`（查看/发给别人用；例：`华硕新商城-_fun_0377_商品发布支持草稿箱功能.xlsx`）。需求编号统一写成 `字母_数字`：文件夹是 `fun1642` 时文件名用 `fun_1642`；已有下划线的保持。需求名去掉 `\ / : * ? " < > |`，空格改 `_`；中文引号可保留。

   - `{项目名}-功能测试用例-执行状态清单.xlsx`（实测执行情况）
   - `{项目名}-功能测试用例-执行过程.md`（逐条可复现手册）
   - 组长评审改完**直接覆盖**该查看版 xlsx，不另存 `-改正后`。只改**之后新生成**的查看版文件名；不主动改历史归档里的旧文件名，除非用户明确要求。
4. 生成用例时如实标注实测情况：已实测通过 / 部分验证 / 当前环境受阻 / 疑似缺陷 / 未执行，并附实测说明；**禁止把未验证或环境无法执行的功能写成已验证**。
5. 生成用例后，在工作区保留源数据 JSON（`cases_*.json`），作为后续重新生成的唯一数据源。
6. 生成 xlsx：数据单元格开启自动换行、数据行不设固定行高（保持自动高度），仅表头可固定高度。
7. 测试用例设计以《测试用例设计规范.md》为准（含覆盖表门禁）。《测试用例设计规范_参考.md》仅作参考。
8. 生成后对照设计规范 §1.2（成功标准逐条有编号）和 §4 自检。组长新意见先泛化写入设计规范 §4；本需求特有的字段值不写进通用清单。读取评审 xlsx 的方法见《组长评审要点_易忽略点清单.md》。

## 四、组长评审表读取规则（固定方法，通用）

收到组长评审后的 xlsx（文件名含 `reviewed by`）时，按以下固定流程读取批注并改回查看版，**禁止反复尝试其他读取方式**：

1. 用 .NET ZipFile 将评审 xlsx 解压到临时目录。
2. 读 `xl/comments1.xml` 取批注正文（每条带单元格引用，如 H2、E7）；读 `xl/drawings/vmlDrawing1.vml` 确认批注位置；读 `xl/sharedStrings.xml` + `xl/worksheets/sheet1.xml` 映射真实单元格值（`t="s"` 的 `<v>` 是 sharedStrings 索引）。
3. 批注行号对应用例编号：第 2 行 = TC_XXX_001，第 3 行 = 002，依此类推；E 列=用例名称列，H 列=预期列。
4. 不依赖 artifact-tool 的 thread/note 检查，不把表格渲染成图片做识别。
5. 按批注修改用例，**直接覆盖**对应需求文件夹里的查看版 xlsx（沿用原表格样式），并同步 CSV / 执行状态清单 / 执行过程（源 JSON 为唯一数据源）；**不另存** `-改正后.xlsx`。导出后把自动生成的 `.xlsx.inspect.ndjson` 副产物移出正式文件夹。

## 五、测试执行证据归档规则（通用，系统级）

执行测试用例、或交付任何需要证明结果的验证结论时，必须附带能证明"通过 / 未通过"的关键证据。

> **证据数量与执行节奏硬上限**见同目录《测试执行精进规则.md》（通过每条 1 份关键凭证；缺陷 ≤1 图 +1 JSON；全量执行 ≤1 次等）。本节省归档结构；数量冲突时以《测试执行精进规则》为准。

1. **求精不求多**：一个证据能证明结论就不需要多个，只保留**最关键的证据**（如关键页面截图、接口响应报文、数据库查询结果、执行日志关键行等）；不堆砌无关截图。
2. **证明力优先**：证据必须能明确区分通过与未通过——通过的给通过态画面/响应；未通过的给失败现场（报错信息、白框/缺失、数据不符、超时等），便于复现排错。
3. **归档结构（每个需求的用例文件夹下固定结构）**：
   - 创建 `证据/` 总文件夹；
   - 在 `证据/` 下按用例编号创建子文件夹 `用例X_证据`（如 `用例一_证据`、`用例二_证据`，与用例编号一一对应）；
   - 每条用例的关键证据放入对应子文件夹，文件名含用例编号便于对照，如 `TC_商品楼层_001_通过.png`、`TC_商品楼层_002_失败-白框.png`；
   - **共享证据**（同一证据覆盖多条用例，如三端共用截图）复制到每个相关用例子文件夹，不只在一条用例下；
   - 生成《实测证据清单_YYYYMMDD.md》放入 `证据/` 总文件夹，表格映射：用例 ↔ 证据文件路径 ↔ 证明内容；
   - 需求文件夹根目录只保留四件套（用例 xlsx、CSV、执行状态清单、执行过程 md），证据统一收进 `证据/`。
4. **配套说明**：证据不能自明时，在实测说明中写清"看哪个证据、对应哪条用例、证明什么结论"。
5. **用途**：方便用户一一对照核对、排错复现、后续复查，以及回归测试时对比新旧差异。

## 六、BUG 反馈文档规范（通用，系统级）

提交/撰写 bug 反馈文档时，统一按以下结构，保证开发可按图索骥、结论可追溯（该写法已获组长认可“写得很详细”，团队沿用）：

1. **基本信息**：标题、所属产品/模块、缺陷类型、优先级/严重程度、发现人/日期、测试环境、账号。
2. **复现步骤**：按顺序写可操作步骤（含前置条件与数据准备），新人可复现，页面路径/接口要具体。
3. **实际结果 vs 预期结果**：实际结果给失败现场（报错、白框/缺失、数据不符、超时等）；预期结果写明确判定标准。
4. **根因分析**：基于证据分析；推断部分明确标注“推断”并给依据（接口时序、HTTP 状态、响应体、对照实验）。
5. **影响范围**：写明受影响模块/状态/数据范围，已排查正常的范围也写清。
6. **证据**：求精不求多（接口报文、HTTP 状态、截图、日志关键行），能区分通过与失败；判定用批量统计/对照实验（如 N 轮复现率、强制时序必现、资源 404 vs 200），不凭“感觉偶现”。
7. **修复建议**：给出可落地方向（前端/后端/存储侧/数据清洗等）。
8. **关联用例**：列出对应用例编号，便于回归跟踪。

附则：
- **非缺陷结论**（存量数据异常、历史链路、环境问题等）仍要写清判定依据，但不计入 bug 交付物；周报/总结中写“已测完/未发现缺陷”。
- **修复复验**：批量跑 N 轮统计通过率，量化“是否修好”，结论可汇报。
